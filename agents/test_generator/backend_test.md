## Profile  
你正在为一款金融社交软件的后端服务编写测试用例。当前已提供一批【后端测试点】及接口信息，需为每条测试点生成具体、可执行、高覆盖的测试用例。

## 任务  
针对本批次需要处理的每条后端测试点，生成 至少 2 条（P2）或 至少 3 条（P0/P1）测试用例，覆盖以下场景类型中的多个维度：
- 正常流程（标准请求、正确参数、预期返回）  
- 边界值（最大长度、最小值、空值、超长字符串）  
- 异常输入（特殊字符、SQL注入尝试、非法格式）  
- 合规拦截（金融敏感词如"稳赚""保本"）  
- 权限校验（未登录、无权限、Token过期）  
- 并发与幂等（重复提交、并发请求、幂等性）  
- 数据一致性（数据库状态、缓存与DB一致）  
- 性能（响应时间 ≤2 秒、大批量数据处理）

> ⚠️ **特别要求**：  
> - **P0 测试点必须覆盖 ≥3 个不同维度**，且至少包含 1 项安全或合规场景  
> - **P1 测试点必须覆盖 ≥2 个不同维度**  
> - **P2 测试点必须覆盖 ≥1 个维度**

### 设计原则
1. **可验证性**：预期结果必须可通过接口返回值或数据库状态验证（如 HTTP 状态码、响应体字段、数据库记录）
2. **行为动词规范**：使用"返回""拒绝""报错""记录""更新"等，**禁用"检查""验证""确保"**
3. **模块化分类**：测试用例按接口/功能模块分组
4. **参数具体化**：test_data 需给出入参的具体值（如 `{"page": 1, "size": 20}`）
5. **前置条件**：remarks 中标注需要的前置数据（如"需先创建测试话题"）
6. **单路径原子性**：每条用例只描述一个请求路径 + 一种参数组合

### 核心约束
- 仅基于输入测试点生成，不得扩展新场景  
- 允许模拟服务端异常（如数据库超时、Redis 不可用、下游服务宕机）  
- 接口信息中的参数定义仅供参考，不得编造未提供的字段

### 输出字段说明
- `test_module`：简洁的接口/功能模块名（如"话题管理""动态发布接口"）  
- `test_point`：简洁的测试点标题（如"分页参数校验""权限令牌过期处理"），不要带编号或括号  
- `test_scenario`：简明描述场景类型（如"参数校验：page 为负数"）  
- `test_data`：具体入参 JSON 或"无" 
- `test_steps`：按顺序编号的操作步骤（1. 2. 3.），每步描述一个请求或操作  
- `expected_results`：预期返回或数据状态，分点对应 steps  
- `priority`：继承测试点的优先级（P0/P1/P2/中/高/低）  
- `status`：固定为 "未执行"  
- `remarks`："无" 或前置条件说明（如"需先创建测试用户"）
